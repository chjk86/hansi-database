# 한시 자동태깅 파이프라인 설계

- 날짜: 2026-08-04
- 상태: 설계 승인, 스펙 검토 대기

## 배경

한시팀(글로벌인문학연구원 추정 프로젝트)은 19개 문집(약 23,000수)의 한시 XML 데이터를
구축 중이다. 각 문집 파일(`태깅_XXX집.txt`)은 이미 `<term>`(시어)과 `<rhyme>`(운자),
`<Charactercount>`(오언/칠언)까지는 1차 자동태깅이 되어 있으나, 다음 항목은 비어 있다.

- `<Form><Basetype>/<Detailtype>` (형식 대/세분류)
- `<Themes>` (주제 분류)
- `<Couplet>` (대장)
- `<term>` vs `<D>` (시어/용어) 재분류 — 기존 태깅은 의미 구조를 고려하지 않고
  기계적으로 분절된 것이라 경계 자체가 부정확할 수 있음

`임백호집_3차완본_20260730.txt`(723수)는 위 항목이 모두 완성된 골드 스탠다드이며,
이 파일의 태깅 패턴을 학습해 나머지 19개 문집의 빈 항목을 같은 수준으로 채우는
자동태깅 프로그램을 만드는 것이 목표다.

이 프로그램의 산출물은 최종본이 아니라, 팀의 기존 사람 검수 워크플로우
(한국고전종합DB 대조, Google Drive/Sheet 제출)에서 검수 부담을 줄이는
고품질 프리필(pre-fill)이다.

## 범위

**포함**
- 형식(Basetype/Detailtype) 판정
- 주제(Themes) 분류 — `category`/`basis`/`evidence`/한글 라벨, 다중 태그 허용
- 대장(Couplet) 배치
- 시어 재분절 및 term/D 재분류

**제외**
- **전고(Allusion)**: 실제 고전 문헌 원문 인용이 필요해 LLM 환각 위험이 크고
  검증 수단(원문 DB 대조)이 없어 이번 범위에서 제외. 추후 별도 작업.
- 평측(平仄), 문법(품사), 의미(의상), 시안(묘처) 등 매뉴얼상 장기 과제로
  명시된 층위(2·4·7)는 다루지 않음.
- 수운(搜韻, sou-yun.cn) 아카이브 대조: 접근 수단이 없어 한어대사전만으로
  term/D를 판정함 (매뉴얼은 두 사전 모두 요구하나 한어대사전만 사용 —
  일부 정확도 트레이드오프 있음을 인지하고 진행).

## 아키텍처

```
[19개 문집 태깅_XXX집.txt]              [임백호집_3차완본] (few-shot 예시)
        │                                       │
        ▼                                       │
 ① 사전 인덱스 구축 (1회, 재사용)                  │
   한어대사전.txt(37만 표제어) → 조회용 인덱스      │
        │                                       │
        ▼                                       │
 ② 시구 분절 (규칙 우선, LLM 없음)                 │
   기존 <term> 위치는 힌트로만 참고, 사전 최장일치로 │
   분절 후보 생성 → 후보가 하나면 확정              │
        │                                       │
        ▼ (분절이 애매한 구간만)                   │
 ③ LLM 분절/term↔D 판정  ◄────────────────────────┤ (매뉴얼 규칙 + 예시, 프롬프트 캐싱)
        │                                       │
        ▼                                       │
 ④ Form 판정 (Basetype/Detailtype)               │
   구수(4구=절구, 8구=율시, 8구 초과=배율) 규칙 우선,│
   고체시 세부갈래(고시/악부/사/부 등)만 LLM  ◄──────┤
        │                                       │
        ▼                                       │
 ⑤ Couplet 배치 (규칙, LLM 없음)                   │
   근체시(절구 제외) 중간 구 쌍을 규칙으로 배치,     │
   판단 유보 시 <C></C> (매뉴얼 규정)               │
        │                                       │
        ▼                                       │
 ⑥ Theme 분류 (LLM, 시 1편당 1회)  ◄────────────────┘ (24개 카테고리표 + 예시, 프롬프트 캐싱)
        │
        ▼
 ⑦ 검증 (규칙 기반, LLM 없음)
        │
        ▼
[완성 XML] + [검토 필요 항목 QA 로그]
```

**원칙**: 사전·구조로 결정 가능한 항목(①②④일부⑤)은 규칙으로 확정하고, 진짜 해석이
필요한 부분(③애매 분절, ④고체시 세부갈래, ⑥주제)에만 LLM을 사용해 비용과 환각
위험을 최소화한다.

## 컴포넌트 상세

### ① 사전 인덱스
`한어대사전.txt`(371,807개 표제어 항목)를 파싱해 표제어 → 존재 여부를 빠르게 조회할
수 있는 인덱스로 변환. 파이프라인 전체에서 1회만 구축해 재사용.

### ②③ 시구 분절 및 term/D 판정
- 사전 기반 최장일치(maximum matching)로 각 시구의 분절 후보를 생성. 기존
  `<term>` 위치는 "대략 이 근처가 의미 단위"라는 힌트로만 참고하고 그대로 신뢰하지
  않는다.
- 분절이 하나로 확정되지 않거나(여러 후보), 매뉴얼의 특수 규칙(부정어 처리,
  3자 안긴어휘, 은유, 어순 도치 lemma 등)이 적용될 만한 구간만 LLM에 판단을 맡긴다.
- 확정된 각 시어 스팬은 사전 등재 여부로 `<term>`/`<D>`를 기계적으로 결정한다
  (이 결정 자체는 LLM이 아니라 사전 조회 결과를 그대로 따름).

### ④ Form (Basetype/Detailtype)
- `Charactercount`는 이미 채워져 있어 작업 불필요.
- 구수 규칙: 4구 → 절구, 8구 → 율시, 8구 초과(짝수 구) → 배율 (모두 근체시).
- 고체시 여부 및 세부갈래(고시·악부·사·부·잡체시·과체시 등)는 구수 규칙만으로
  판정하기 어려워 LLM 판단이 필요.

### ⑤ Couplet (대장)
- 근체시(절구 제외)에서 첫 구-쌍과 마지막 구-쌍을 제외한 중간 구-쌍에 규칙으로
  `<Couplet>`을 배치 (율시: 3-4구, 5-6구 / 배율: 첫·끝 쌍 제외한 모든 중간 쌍).
- 매뉴얼 규정대로 판단이 애매한 경우 `<C></C>`로 유보 표시.

### ⑥ Theme (주제 분류) — 신뢰도 강화 장치 포함
- 제목을 24개 카테고리 키워드표로 먼저 규칙 기반 스캔해 후보 생성.
- LLM은 "후보 확인 + 본문 근거 기반 추가 주제 탐색"을 수행 (백지 판단이 아님).
- **근거 실재성 검증**: LLM이 제시한 `evidence` 문자열이 실제로 해당 시의
  제목/본문에 존재하는지 사후 대조. 존재하지 않으면 환각으로 간주해 자동 반려·재시도.
- **저신뢰 플래깅**: 근거가 빈약하거나(예: evidence 1개뿐) 카테고리 경계가 애매한
  경우 QA 로그에 기록해 사람 검수 우선순위로 삼는다.

## 데이터 흐름 및 출력 형식

**입력** (원본은 그대로 두고 절대 덮어쓰지 않음)
- `extracted/대상데이터.../태깅_XXX집.txt` (19개 문집)
- `임백호집_3차완본_20260730.txt` (few-shot 예시 소스)
- `한어대사전.txt` (사전 인덱스 소스)

**출력**
```
hanshi-tagging/
  output/
    완성본_지천집_황정욱_자동태깅_20260804.xml
    완성본_눌재집_박상_자동태깅_20260804.xml
    ...
  qa/
    지천집_검토필요_20260804.csv
    ...
  logs/
    run_20260804.log
```
- 파일명은 팀 기존 명명 규칙(`완성본_문집명_작자명_작업자명`)을 따르되
  작업자명 자리에 `자동태깅`을 사용. 작자명은 원본 `<Author>`에서 자동 추출.
- QA 로그 컬럼: `poem_id, collection, 항목, 사유`

**처리 단위 & 재개 가능성**
문집 단위 + 시 단위로 처리 상태를 기록해, 중단 후 재실행 시 이미 처리된 poem id는
건너뛰고 이어서 진행한다.

## 에러 처리 및 검증

**처리 중 오류 대응**
- LLM 호출 실패(레이트리밋·타임아웃): 지수 백오프로 재시도, 계속 실패하면 해당
  시를 건너뛰고 QA 로그에 "처리 실패"로 기록 — 전체 실행은 중단되지 않음.
- 사전 인덱스에 없는 이체자/OCR 오류 등: 매칭 실패로 처리하고 QA 로그에 표시,
  파이프라인은 계속 진행.

**출력 검증 (규칙 기반, 실행 후 자동 수행)**
- XML 정형성(well-formed) 검사
- Theme `evidence` 인용 글자의 본문/제목 실재 여부 대조
- term/D 태깅이 원문 글자를 훼손하지 않았는지 대조 (태그 제거 후 원문과 일치해야 함)
- `<Couplet>`이 근체시(절구 제외)에만, 올바른 구 쌍에만 씌워졌는지 확인

## 테스트 및 롤아웃 계획

1. **골드 검증**: 임백호집 723수 중 약 100수를 hold-out으로 감춰 파이프라인 예측과
   실제 사람 태깅을 대조 — 항목별(특히 Theme) 정확도를 수치로 확인하고 필요시
   프롬프트를 조정한다. 나머지 약 620수는 few-shot 예시 소스로 계속 사용한다.
2. **파일럿 (지천집, 224수)**: 실제 문집 1개를 전체로 돌려 완성본 XML과 QA
   로그를 생성한다.
3. **사람 검토**: 파일럿 결과 표본을 원본과 직접 대조(before/after)해 품질을
   확인한다.
4. **확대 실행**: 파일럿이 만족스러우면 나머지 18개 문집으로 확대한다.

## 리스크 및 한계

- 수운 아카이브 미사용으로 인해 매뉴얼이 요구하는 이중 사전 검증보다 term/D
  판정 정확도가 낮을 수 있음 — 골드 검증 단계에서 이 영향을 함께 측정한다.
- 전고(Allusion)는 이번 범위에서 완전히 제외 — 최종 데이터는 여전히 사람이
  전고 층위를 별도로 채워야 한다.
- Theme 분류는 근본적으로 해석적 판단이 개입하는 영역이라 완전한 자동화
  정확도는 보장할 수 없음 — 신뢰도 강화 장치와 사람 검수로 보완한다.
