# 단계별 파이프라인 + 3모델 비교 실험 설계

- 날짜: 2026-08-05
- 상태: 설계 승인, 스펙 검토 대기

## 배경

지천집 224수 파일럿 결과를 사용자가 직접 검토한 결과, term/D(시어) 분류와 Theme(주제) 분류
품질이 만족스럽지 않았다. 두 가지 가설을 세웠다:

1. **한어대사전 오염 가설**: term/D 판정 시 LLM에게 "이 후보는 사전에 있다/없다"는 신호를
   함께 보여주는 현재 방식이, 매뉴얼이 요구하는 문맥적·문학적 판단(부정어 처리, 3자
   안긴어휘, 은유, 어순도치 등)을 건너뛰고 "사전에 있으면 term" 식의 얕은 규칙으로
   LLM을 유도할 수 있다.
2. **호출 번들링 가설**: Theme은 사전을 전혀 쓰지 않는데도 품질이 낮다는 점은, 형식·대장·
   주제 세 가지 성격이 다른 판단(구조적/관계적/의미적)을 한 번의 호출에 욱여넣은 것
   자체가 원인일 가능성을 보여준다.

두 가설을 검증하기 위해 (a) 사전을 term/D LLM 입력에서 완전히 제거하고, (b) 네 항목을
각각 단일 목적 호출로 분리하며, (c) 사용자가 새로 확보한 중개 API(Timely, OpenAI 호환
REST)를 통해 서로 다른 3개 회사의 최상위급 모델(Claude Opus 4.7 / Gemini 3 Flash
Preview / GPT-5.5)로 같은 지천집 50수를 돌려 비교한다.

이번 작업은 **실험**이다. 기존에 검증·파일럿까지 마친 프로덕션 파이프라인(`src/`,
`scripts/run_pilot.py`)은 건드리지 않고, 별도 스크립트로 결과를 확인한 뒤 반영 여부를
다시 결정한다.

## 범위

**포함**
- 시어(term/D) 판정에서 한어대사전을 LLM 입력에서 제거하고 사후 라벨링 전용으로 전환
- 형식→대장→시어→주제 순, 4개의 단일 목적 LLM 호출로 분리 (기존 "형식+대장+주제 통합
  1회" 설계를 대체)
- Timely 중개 API 연동 (`TimelyLLMClient`, OpenAI 호환 REST)
- 지천집 50수 × 3모델 비교 실험 스크립트와 비교 리포트

**제외**
- 기존 프로덕션 파이프라인(`src/pipeline.py`, `src/term_classify.py`,
  `src/interpretive_classify.py` 등)의 실제 교체 — 이번 실험 결과를 사용자가 검토한
  뒤 별도로 결정
- 전고(Allusion) — 여전히 범위 밖
- 나머지 18개 문집 확대 — 이번 실험이 끝나고 결정

## 아키텍처

```
[지천집 시 1편] (원문 시어 태깅 제거, 순수 텍스트 + 운자 위치만 유지)
        │
        ▼
 ① 형식(Form) 호출
   LLM: Basetype 판단 (+ 고체시인 경우만 Detailtype 세부분류)
   규칙: 근체시로 확정되면 Detailtype은 구수로 결정 (4구=절구/8구=율시/
         8구초과=배율) — LLM 재호출 없음
        │
        ▼
 ② 대장(Couplet) 호출 — 근체시 & 절구가 아닐 때만 호출 (절구·고체시는 생략)
   LLM: 중간 구-쌍 중 실제 대장인 것만 표시
        │
        ▼
 ③ 시어(term/D) 호출 — 사전 정보 없이 순수 문맥 판단
   LLM: 시구별로 의미 있는 시어 경계만 판단 (기존 <term> 태깅은 힌트로도
        보여주지 않음 — 완전히 새로 판단)
   규칙(사후): 확정된 각 구간을 한어대사전 조회 → 등재 시 term, 미등재 시 D
   (LLM은 사전 존재 여부를 전혀 모른 채 경계만 판단)
        │
        ▼
 ④ 주제(Theme) 호출
   LLM: ③에서 확정된 term 태깅이 포함된 시 전체를 보고 주제 분류
        (evidence 환각 검증은 기존과 동일하게 유지)
        │
        ▼
[모델별 완성 XML] × 3 (Claude Opus 4.7 / Gemini 3 Flash Preview / GPT-5.5)
        │
        ▼
[3모델 비교 리포트] (시 50편 각각에 대해 3모델 결과를 나란히 배치)
```

**시 1편당 LLM 호출 수**: 절구·고체시는 3회(①②생략시 대장 없음, 실제로는 ①②③④ 중
②만 생략되므로 3회), 그 외 근체시는 4회. 기존 설계(최대 2회)보다 늘어나지만, 사전이
LLM 판단을 흐리지 않고 각 호출이 한 가지 목적에만 집중한다는 가설을 검증하는 것이
목적이므로 이번 실험에서는 비용보다 품질 신호 확보를 우선한다.

## 컴포넌트 상세

### TimelyLLMClient
- Timely는 OpenAI 호환 REST API(`https://hello.timelygpt.co.kr/api/v2/chat/bridge/openai`)를
  제공하므로, 표준 `openai` Python 패키지를 `base_url`만 바꿔서 그대로 사용한다.
- 기존 `LLMClient` 프로토콜(`complete(system, user, response_schema) -> dict`)을
  그대로 구현 — Gemini/Fake와 동일한 인터페이스이므로 실험 스크립트가 모델 종류에
  무관하게 동일한 파이프라인 코드를 재사용한다.
- 인증: 환경변수 `TIMELY_API_KEY`.
- Rate limit이 크레딧 잔액에 따라 동적으로 변한다(정상 60/분 → 크레딧 부족 시 10/분,
  2 미만이면 차단). 429 응답 시 기존보다 긴 대기(예: 10초 이상)를 두고 재시도하는
  백오프를 적용한다. 402(크레딧 부족)는 재시도해도 소용없으므로 즉시 실패 처리하고
  QA 로그에 명확히 표시한다.
- 모델 이름은 `"anthropic/claude-opus-4.7"`처럼 provider/model 형식 문자열을 그대로
  전달한다.

### Form/Couplet/term-D/Theme 각 단계
- 각각 별도 함수로 분리 (기존 `interpretive_classify.py`의 통합 함수를 실험용으로
  4개 함수로 쪼갠 새 모듈, 예: `experiments/staged_classify.py`).
- term/D 함수는 입력으로 완전히 태깅되지 않은 순수 시구 텍스트만 받는다(기존
  `<term>` 태깅 제거). 사전 조회는 LLM 호출 이후, 별도의 순수 함수로 분리되어
  `DictIndex.contains()`만 사용한다 — LLM 프롬프트 생성 코드는 `DictIndex`를
  아예 import하지 않는다 (사전이 프롬프트에 새어 들어가지 않음을 코드 구조로 보장).
- Theme 함수는 ③에서 반환된 term 태깅 결과를 입력으로 받아 프롬프트에 포함한다.
- 기존 evidence 환각 검증(`_evidence_exists_in_poem`, 제목/본문 경계 구분자 포함)은
  그대로 재사용한다.

## 데이터 흐름 및 출력

**입력**: `extracted/대상데이터_제목내용시어운자대장태그/태깅_지천집.txt`에서 파일
순서상 처음 50수. 골드 스탠다드가 없어 무작위 추출의 이점이 없고, 고정된 순서를
써야 재실행 시 결과를 재현·재비교할 수 있다.

**출력**
```
experiments/2026-08-05-model-comparison/
  output_claude-opus-4.7.xml
  output_gemini-3-flash-preview.xml
  output_gpt-5.5.xml
  comparison_report.txt   ← 시 50편 각각에 대해 3모델 결과를 나란히 배치
  qa_log.csv              ← 모델별 처리 실패/환각 의심 등 통합 기록 (model 컬럼 추가)
```

`comparison_report.txt`는 각 시마다: 원문 → (Claude 결과) → (Gemini 결과) →
(GPT 결과) 순으로 나열해 사람이 스크롤하면서 세 모델의 형식/대장/시어/주제 판단을
바로 대조할 수 있게 한다.

## 에러 처리 및 검증

- 기존 파이프라인의 검증 로직(`validate_poem`의 원문 훼손 검사, evidence 환각 검사)을
  세 모델 각각의 출력에 동일하게 적용 — 모델별 QA 로그 행 수/유형을 비교하는 것 자체가
  하나의 품질 신호가 된다.
- 한 모델이 크레딧 부족(402)이나 반복된 429로 중단되더라도 나머지 두 모델은 계속
  진행 — 모델별로 독립된 실행 단위로 격리한다.

## 테스트 및 롤아웃 계획

1. 파이프라인 로직(Form/Couplet/term-D/Theme 각 단계 함수, TimelyLLMClient)은
   FakeLLMClient로 단위 테스트.
2. 지천집 50수 × 3모델 실제 실행 (실 API, 사용자가 직접 결과 검토).
3. 비교 리포트를 사용자가 검토하고, 어느 모델/어느 변경(사전 제거·단계 분리)이
   실제로 품질을 개선했는지 판단 → 프로덕션 파이프라인 반영 여부를 별도로 결정.

## 리스크 및 한계

- 지천집은 골드 스탠다드가 없어 정량적 정확도 측정이 불가능 — 이번 실험은 사람이
  직접 세 모델의 출력을 눈으로 비교하는 정성적 평가다.
- 호출 수가 늘어 비용이 커진다(시 1편당 최대 4회 × 3모델 × 50수 = 최대 600회
  호출). Claude Opus 4.7는 특히 단가가 높은 모델이라 앞선 Gemini 파일럿보다 비용이
  유의미하게 커질 수 있다 — 실행 전 사용자에게 대략적인 비용 추정을 다시 안내한다.
- Timely의 rate limit이 크레딧 잔액에 연동되어 있어, 실행 중 크레딧이 소진되면
  자동으로 요청 속도가 느려지거나 중단될 수 있다.
